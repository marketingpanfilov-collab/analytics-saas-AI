# План внедрения тарифной логики Free → Starter → Growth → Scale (BoardIQ)

**Статус:** финал для утверждения (без кода в этом документе; реализация — после подтверждения).  
**Основа:** `PlanFeatureMatrix` (`starter` | `growth` | `scale`), `billingUiContract`, `billingShellResolver`, widget gating (LTV / Reports / Attribution), `dashboardFreshness` (TTL), лимиты проектов / мест / аккаунтов / weekly reports.  
**Free:** не slug в Paddle, **виртуальный уровень** через сочетание billing state (`no_subscription` + пользователь в продукте) и отдельной **логики матрицы возможностей Free** (не подменяет тип `PlanFeatureMatrix`, не ломает контракт).

**Что не меняется (архитектура и контракты):** общая схема Next.js / Supabase / API; структура и смысл `PlanFeatureMatrix` и перечень полей; `billingUiContract`; существующие механики gating. Допустимо: новые ветки поведения resolver/bootstrap и продуктовый слой (виртуальный tier Free), тексты UI.

---

## Модель доступа Free (`no_subscription`) — архитектурное решение

**Проблема в коде сегодня:** при `access_state === "no_subscription"` запрещён analytics read (в т.ч. `GET /api/dashboard/bundle` → 402) и heavy sync; при отсутствии подписки `plan_feature_matrix` сводится к `unknown` → ломает Reports/LTV через матрицу. Продуктовый план требует: реальные данные, first value, initial sync — без поломки paid, invited и billing flow.

### Сравнение вариантов

| Вариант | Суть | Плюсы | Минусы |
|--------|------|-------|--------|
| **A — Ослабить `accessState`** | Разрешить read/sync для `no_subscription` при наличии проекта и т.п. прямо в `accessStateAllowsAnalyticsRead` / heavy sync | Мало точек на первый взгляд | Одно значение `no_subscription` = и «вне продукта», и «Free»; легко забыть маршрут или переоткрыть доступ; сложные edge cases (invite, transfer, несколько орг) |
| **B — Явный продуктовый tier (выбрано)** | `access_state` остаётся истиной Paddle; в bootstrap добавляется **`experience_tier`** (или `effective_product_tier`): например `free` \| paid-уровни; API: `paidПравило OR (freeПравило + предикаты)`; виртуальная матрица Free **не** как голый `UNKNOWN` | Чистое разделение биллинг vs опыт; paid/invited проверяются первыми; один канон в bootstrap | Нужна единая политика во всех gates; формула `free` должна быть безошибочной |
| **C — Только фон / read-only bundle** | User sync запрещён; данные только cron/backfill | Узкая атака surface | Initial sync и first value часто не сходятся с UX; тяжёлая поддержка |

### Выбор: **вариант B**

**Почему:** сохраняется строгая семантика `access_state` для биллинга; явный `experience_tier === "free"` даёт проверяемый критерий для API и UI; виртуальная матрица Free отделяется от `getPlanFeatureMatrix("unknown")`; starter / growth / scale и приглашённые на платную орг не ухудшаются.

**Остающиеся риски:** расхождение bootstrap и gate при правках только с одной стороны; ошибка предикатов «орг без подписки»; абьюз без rate limits; путаница копирайта Free vs churn (read-only unpaid).

### Поведение Free (зафиксировано)

**Доступ к bundle и прочим analytics read:** разрешён, если одновременно: `access_state === "no_subscription"` в биллинг-контексте; **`experience_tier === "free"`** в bootstrap; пользователь авторизован и имеет доступ к `project_id`; выполнены предикаты орг/проекта (например `has_any_accessible_project`, согласованность биллинг-орг с проектом); не применяются более жёсткие состояния (`refunded` и т.д. по политике).

**Heavy sync (refresh, OAuth save, insights sync и т.п.):** разрешён по той же схеме `paid OR (free + предикаты + продуктовая политика интенсивности)` — капы по времени/числу выносятся в спеку реализации, но архитектурно gate единый.

**Закрыто для Free (смысл, не только HTTP):** возможности вне виртуальной матрицы Free; лимиты кабинетов/мест/проектов/weekly — как сейчас на соответствующих роутов; явно платные сценарии по продукту.

**Отличия от других случаев:**

| Случай | Как отличить |
|--------|----------------|
| Старый `no_subscription` без Free | Нет `experience_tier === "free"` → поведение как сейчас (PAYWALL / 402 на read) |
| unpaid / expired | Другой `access_state`; не ветка Free; свои баннеры |
| Invited на платную орг | Подписка/entitlement орг → paid path; `experience_tier` не `free` |
| Invited в орг без подписки | Тот же `experience_tier`, что у владельца (единообразие); лимиты орг |

### Уровень API (логика)

1. Bootstrap (`/api/billing/current-plan`): `access_state`, `plan_feature_matrix` (для Free — **виртуальная матрица**), плюс **`experience_tier`**.  
2. Analytics read: `paidAnalyticsRead(access_state) || freeAnalyticsRead(experience_tier, context)`.  
3. Heavy sync: `paidHeavySync(access_state) || freeHeavySync(experience_tier, context, policy)`.  
4. Клиент: placeholder’ы и бейджи опираются на bootstrap + `resolved_ui_state`; **не** выводят Free только из `access_state`.

### Где меняется логика (концептуально)

- Сборка billing payload (`loadBillingCurrentPlan` / `assembleBillingPayload`): вычисление `experience_tier` и подстановка матрицы Free.  
- Единый слой policy для [`requireBillingAccess`](app/lib/auth/requireBillingAccess.ts) / [`accessState`](app/lib/accessState.ts) (или эквивалент), чтобы не дублировать условия по десяткам роутов.  
- При необходимости — точечные ветки [`billingShellResolver`](app/lib/billingShellResolver.ts) / [`BillingShellGate`](app/app/components/BillingShellGate.tsx) **только** для `experience_tier === "free"`, без смешения с unpaid/expired.

### Перед кодом — обязательная проверка

1. Документ с **точной формулой** `experience_tier === "free"` (все предикаты).  
2. Полный **инвентарь роутов** с `billingAnalyticsReadGate*` и `billingHeavySyncGate*`.  
3. Согласование **виртуальной матрицы Free** с лимитами на save routes (кабинеты, проекты, места, weekly).  
4. Инвариант: paid-like `access_state` **не хуже** текущего поведения.  
5. Инвариант: `refunded` **не** проходит через free read/sync.  
6. Спека **капов sync** для Free (unlimited vs ограниченно).

Этот блок **дополняет** раздел **§18 Billing-логика** и pre-implementation audit: без реализации варианта B продуктовый Free (bundle + sync + матрица) **несовместим** с текущими gates «в лоб».

## 1. Модель тарифов

| Уровень | Что это | Позиционирование (ценность) |
|--------|---------|------------------------------|
| **Free** | Виртуальный tier | Пользователь **видит, что происходит** (факты, агрегаты, первый инсайт). **Не получает** уверенности в причинах и перераспределении бюджета на уровне «почему» и полной глубины. |
| **Starter** | Первый платный slug | **Закрывает базовые операционные задачи** в рамках лимитов матрицы: уверенно действовать в одном проекте и масштабе Starter (без «потолка Free» на решения). |
| **Growth** | Slug `growth` | Пользователь **понимает бизнес**: причины, эффективность, прибыльность, единая сводка, команда и несколько проектов — в рамках текущей матрицы. |
| **Scale** | Slug `scale` | **Контроль системы**: снятие потолков `max_*`, максимальная частота обновления данных (TTL). |

**Воронка:** ценность (Free) → осознанный потолок (usage + глубина) → ограничение как оффер → апгрейд (Starter → Growth → Scale).

**Почему платят:** чтобы перейти от «вижу цифры» к «понимаю причинно-следственные связи и управляю» и далее к «контролирую на масштабе без трения».

## 2. Feature mapping (упаковка существующего функционала)

| Возможность (как в коде) | Free | Starter | Growth | Scale |
|--------------------------|------|---------|--------|-------|
| **dashboard_bundle** (сводка + ряды + KPI) | Да: **реальные данные**, достаточно для first value | Полный базовый доступ в лимитах slug | Как Growth по глубине + TTL выше Starter | Как Growth + лучший TTL |
| **attribution_heavy** (тяжёлые блоки на `/app`) | После first value — gate с оффером ценности | Нет (как в матрице Starter) | Да | Да |
| **ltv_full_history** | После first value — урезанный срез + оффер полной истории | Урезано (как Starter) | Полная история | Полная история |
| **marketing_summary** (Reports) | После first value — gate (явная free-матрица, не `unknown`) | Да (как в матрице) | Да | Да |
| **weekly_report_quota** | После first value — квота жёстче или равна Starter (число в рамках существующего счётчика) | Лимит месяца (как Starter) | Без лимита | Без лимита |
| **OAuth / ad accounts** | Достаточно для first value; дальше — лимит `max_ad_accounts` | 3 | 10 | без лимита |

| **TTL** (`dashboardFreshness`) | Редко (не чаще порога Starter: 6 ч как ориентир) | 6 ч | 3 ч | 15 мин |

## 3. First value moment

| Элемент | Фиксация |
|--------|----------|
| **Какой инсайт** | Один **явный** сигнал на дашборде из уже существующей сводки: например **«где сосредоточен расход / доминирующий источник»** или **«перекос бюджета между подключёнными источниками»** — на основе totals и разбивки по источникам/кабинетам за период. |
| **Интерпретация, не только цифры** | Пользователь видит **вывод в человеческом виде**: не сухую таблицу как единственный носитель смысла, а **одну фразу-пояснение** рядом с метрикой (данные → интерпретация → понимание). Технически это упаковка тех же агрегатов из bundle без новых источников данных. |
| **Где** | **`/app`**, зона верхней сводки / KPI (`AppDashboardClient`), до скролла к gated-блокам атрибуции. |
| **За счёт каких данных** | Ответ **`/api/dashboard/bundle`**: реальные Meta / Google / TikTok после успешного sync. |
| **Условия** | Инсайт **до** paywall-оверлея; экран **не пустой** при подключённом источнике и данных; без источника — онбординг, не «тариф пустой». |

**Примеры формулировок вывода (ориентиры для копирайта):**

- «**Около 80% бюджета** за период приходится на **один канал** — остальные источники дают малую долю расхода.»
- «**Основной источник трафика** по показам/кликам за выбранный период — **X** (подставляется доминирующий источник из разбивки).»
- «**Бюджет распределён неравномерно**: расход сосредоточен в одном-двух кабинетах/сетях — перекос виден по долям в сводке.»

Цепочка для пользователя: **данные** (агрегаты) → **интерпретация** (одна явная мысль) → **понимание** («что это значит для моего маркетинга сейчас»).

## 4. Усиление first value

**Задача:** превратить агрегаты из bundle в **инсайт с первого взгляда**, без ожидания скролла и без глубокой атрибуции.

| Аспект | Фиксация |
|--------|----------|
| **Как из агрегатов получается инсайт** | Берутся уже существующие totals и разбивка по источникам/кабинетам; на их основе задаются **правила отображения одного приоритетного вывода** (доминанта по расходу, по трафику, или флаг сильного перекоса при пороге доли — конкретные пороги в продуктовой спеке реализации). |
| **Где отображается** | **Верх дашборда** `/app`, в одной визуально выделенной зоне (над или внутри первого блока KPI), чтобы попадало в первый экран без прокрутки на типичных разрешениях. |
| **Почему критично для конверсии** | Пользователь **сразу** получает ощущение «продукт дал ответ», а не «я сам должен стать аналитиком». Это снижает трение до первого «ага» и делает последующий gate (атрибуция, LTV, отчёты) **продолжением** истории («хочу докопаться глубже»), а не первым контактом с ценностью. |

Связь с §3: §3 задаёт смысл и примеры; §4 — **как усилить подачу** (место на экране, приоритет одного вывода, пороги интерпретации).

## 5. Глубина инсайта (Free vs Growth)

| Tier | Уровень ответа |
|------|----------------|
| **Free** | **Что** происходит: объёмы, доли, тренд в базовой сводке. |
| **Starter** | **Что** + **действовать** в базовом масштабе (лимиты матрицы), без полной «почему» тяжёлой атрибуции и полной LTV-истории. |
| **Growth** | **Почему** и **где эффективность / прибыль / потери**: attribution heavy, полная LTV, marketing summary, weekly без квоты, выше лимиты. |
| **Scale** | **Почему** + **контроль на масштабе и во времени** (лимиты сняты, TTL минимальный). |

Копирайт gate: не «функция открылась», а **«отвечаете на вопрос почему / куда переложить бюджет / окупается ли канал»**.

## 6. Free-логика (зафиксировано)

1. **Initial sync разрешён** — данные до first value.  
2. **Данные доступны** — базовый bundle не скрывается политикой «пустой дашборд».  
3. **Ограничения после first value** — глубина (attribution, LTV, Reports), usage pressure (TTL, кабинеты, квоты).  
4. **Запрещено:** пустой дашборд как норма Free; полная блокировка аналитики при наличии данных.

## 7. Paywall = продажа

**Общий акцент:** на Free пользователь **видит только часть картины** — этого **недостаточно, чтобы уверенно принимать решения** о перераспределении бюджета, окупаемости каналов и масштабировании. Апгрейд = **полнота картины и опора для решений**, а не «включили кнопку».

**Запрещено в копирайте:** «недоступно», «заблокировано». **Предпочтительно:** «вы видите **только часть картины**», «чтобы **дойти до вывода, на который можно опереться** — …».

**Структура оффера:** что сейчас **упрощено / не хватает для уверенных решений** → что **появится после апгрейда** → **зачем бизнесу**.

| Ограничение | Сейчас (часть картины / недостаточно для решения) | После апгрейда | Зачем бизнесу |
|--------------|---------------------------------------------------|----------------|---------------|
| Attribution heavy | **Нельзя уверенно сказать, за счёт чего** работает результат — видны расходы и поток, но не полная связка вкладов | Полные виджеты на дашборде | Перенос бюджета **с обоснованием** |
| LTV (не полная история) | **Нельзя оценить окупаемость** на горизонте нескольких циклов | Полная история LTV | Решения о **масштабе** и удержании |
| Reports | **Нет одной цельной картины** для совещаний и согласований | Сводный отчёт | Согласования и **меньше ручной сборки** |
| Weekly report quota | **Нельзя закрепить регулярную картину** для команды в привычном ритме | Без потолка (Growth+) | Экономия времени |
| Лимит аккаунтов | **Картина по портфелю кабинетов неполная** | Больше кабинетов | Мультибренд **без слепых зон** |
| Проекты / места | **Нельзя масштабировать работу** в продукте под команду | Рост лимитов | Рост команды **без хаоса** |
| TTL | **Решения на устаревшем снимке** рынка для тактического ритма | Свежие агрегаты | Управление **в деньгах дня** |
| Частый manual refresh (если политика) | **Нельзя держать дашборд в том ритме обновления**, который нужен при частых изменениях | Приоритет / снятие лимита | Кампании меняются **часами** |

## 8. Upgrade triggers

| Точка | Триггер | UI | Сценарий апгрейда |
|-------|---------|-----|-------------------|
| **LTV** | Заход на `/app/ltv` или смена окна | Placeholder / LIMITED + CTA | Inline pricing / модалка → Starter или Growth → checkout |
| **Reports** | Переход на `/app/reports` | То же | То же |
| **Attribution** | Скролл до тяжёлой атрибуции на `/app` | Placeholder с продающим текстом | То же (**основной драйвер**, см. §14) |
| **Аккаунт** | Включение кабинета сверх лимита | Ответ API + баннер у списка | Апгрейд на больший `max_ad_accounts` |
| **Обновление данных** | Частый refresh / «данные отстают» | Inline CTA + баннер TTL + **urgency** (§13) | Апгрейд за свежесть (Growth / Scale) |
| **Период** | Длинный диапазон — **только если** согласовано продуктом; иначе v1: TTL + глубина экранов | Подсказка у range или banner | Продажа Growth как стратегическая глубина |

## 9. Usage pressure

| Рычаг | Как работает | Цель |
|--------|--------------|------|
| **Глубина анализа** | Free = факты; «почему» — за Starter/Growth | Потолок **понимания**, не отключение входа |
| **TTL** | Free реже обновляет снимок | Мотивация следующего tier |
| **Refresh** | Не резать первый sync; ограничивать **частоту** ручного обновления только осознанной политикой | Трение оператора, не «чёрный экран» |
| **Период** | Опционально, если есть решение; иначе не вводить новую механику в v1 | Доп. давление |

## 10. Intent-based upgrade

**Условие:** в сессии **≥ 3 осмысленных действия** (например: `/app`, смена периода/источника, переход LTV/Reports или скролл к атрибуции) — порог фиксируется в спеке.

**Показ:** баннер или компактная модалка: **«Готовы увидеть полную картину?»** + связка «уже видите → не хватает для почему» + CTA (Starter минимальный чек или Growth — по ценовой стратегии). Частота: cap (например 1× за сессию / день). **Слой срочности** (§13) можно кратко вплести: «картина обновляется реже на Free — на платном шаге вы ближе к актуальному дню».

**Технически:** существующие `BillingPricingModalProvider` + клиентский учёт событий.

## 11. Before / After

**Назначение:** визуально и смыслово зафиксировать разницу «до / после» апгрейда с глубины Free к Growth (Starter — переходный шаг по §5).

| Измерение | **Free (before)** | **Growth (after)** |
|-----------|-------------------|---------------------|
| **Дашборд** | **Агрегаты**, доли, тренд; **базовая картина** «куда уходят деньги и трафик» | **Прибыльность и эффективность**, **убыточные и сильные каналы**, полная атрибуционная аналитика в рамках продукта |
| **LTV** | Урезанный срез | Полная история, опора для решений по окупаемости |
| **Reports** | Нет единой сводки | **Полная аналитика** в формате маркетинговой сводки |
| **Данные** | Реже обновляются (TTL) | Чаще — **полнота картины во времени** |
| **Ощущение** | «Вижу часть картины» | «Понимаю бизнес» |

Starter — между ними по **глубине «почему»**, но снимает ограничения Free и даёт полноту базовых задач в лимитах slug.

## 12. Data pressure (TTL)

| Tier | Восприятие |
|------|------------|
| **Free** | Обновления **реже** — ок для недельного взгляда, мало для почасового управления |
| **Growth** | **Чаще** (3 ч) |
| **Scale** | **Почти real-time** (15 мин) |

Копирайт у свежести: «для более свежей картины — тариф X», не «устарело».

---

## 13. Urgency layer

**Цель:** ускорить принятие решения об апгрейде за счёт **осознанного дискомфорта** («моя картина отстаёт / неполна»), без агрессии и без нарушения §6 (никакого полного отключения данных до ценности).

| Tier | Сообщение уровня urgency |
|------|---------------------------|
| **Free** | Данные обновляются **реже**; пользователь **осознанно видит неполную картину** для операционных и стратегических решений (согласовано с §7). |
| **Growth** | Данные обновляются **чаще**; доступна **полная аналитическая картина** по продукту (атрибуция, LTV, отчёты, лимиты). |
| **Scale** | **Почти real-time** по TTL + снятие потолков — «контроль в ритме дня». |

**Где применять единый нарратив (короткие формулировки, без «недоступно»):**

| Точка касания | Как использовать |
|---------------|------------------|
| **Рядом с freshness** | Одна строка: «На Free снимок обновляется реже — **чтобы оперировать свежей картиной**, рассмотрите Growth/Scale» (конкретный tier под цель). |
| **В paywall / placeholder’ах (§7)** | Второй абзац или подзаголовок: «Сейчас вы видите **часть картины**; **полная картина для решений** — на следующем шаге». |
| **В баннерах** | Для Free: мягкий deadline-ощущение по **актуальности** и **глубине**, не по «блокировке аккаунта». |
| **В upgrade modal** | Блок «почему сейчас»: **скорость обновления** + **полнота выводов**; CTA ведёт в checkout. |

Связь с §12: **Data pressure (TTL)** задаёт факты; **Urgency layer** — **как их формулировать** для конверсии.

## 14. Primary upgrade driver

1. **Attribution** — главный мост от «что тратим» к «куда переложить»; совпадает с крупным placeholder на дашборде.  
2. **LTV** — второй: окупаемость и горизонт.  
3. **Reports** — третий: сводка для команды.

Порядок акцентов в модалке тарифов: **Attribution → LTV → Reports**.

## 16. CJM

1. Login → bootstrap.  
2. Onboarding → проект.  
3. Подключение → **initial sync**.  
4. **`/app` → first value** (интерпретация + §4).  
5. Исследование (период, экраны, атрибуция).  
6. **Intent** → «полная картина» + при необходимости **urgency** (§13).  
7. Gate с оффером (§7).  
8. Checkout → Starter / Growth / Scale.  
9. Удержание: TTL и лимиты → следующий tier.

## 17. UI-изменения (описание)

- **`/app`:** блок first value + зона усиления (§4); единый шаблон placeholder’ов (§7); TTL-копирайт (§12) + **urgency** (§13).  
- **LTV / Reports / Attribution:** один тон оффера («часть картины» → полнота для решений).  
- **Баннеры:** Free ≠ churn read-only; баннеры Free используют **urgency layer**.  
- **Сайдбар / топбар:** бейдж Free; CTA «Полная картина».  
- **Intent-modal** (§10) + **upgrade modal** с блоком urgency (§13).  
- **Настройки:** лестница Free → Starter → Growth → Scale в языке решений.

## 18. Billing-логика

- **Канон доступа Free в API:** раздел **«Модель доступа Free (`no_subscription`) — архитектурное решение»** выше (`experience_tier` + виртуальная матрица + единая политика gates); без этого shell и матрица не совпадут с `requireBillingAccess` / bundle.
- **`no_subscription` без входа в продукт** — можно оставить **PAYWALL** (не обещать дашборд без онбординга).  
- **`no_subscription` + проект и данные** — **не** вечный PAYWALL: **DASHBOARD** + виртуальная матрица Free + `allowed_actions` с sync для first value и чтения bundle.  
- **READ_ONLY unpaid/expired** — сценарий **возврата оплаты**, не Free.  
- **`plan_feature_matrix`:** для Free — **явная виртуальная матрица**, не **`unknown`**.  
- Платные slug: **starter / growth / scale** без изменений.

---

## 19. Риски

- Убить **first value** (запрет sync/bundle на Free).  
- Смешать **Free** и **churn**.  
- Free ≈ **Growth** — нет мотивации на Starter.  
- Регрессия **приглашённых**.  
- Расхождение **лендинг ↔ продукт**.  
- **Перегнуть urgency** — токсичные «дедлайны» без ценности → отток.

### Critical constraints (нельзя нарушать)

| Ограничение | Смысл |
|-------------|--------|
| **Нельзя ломать first value** | Без явного инсайта и интерпретации (§3–§4) воронка не стартует. |
| **Нельзя делать пустой дашборд** | Пустой экран при наличии подключённых данных и sync — провал доверия и конверсии. |
| **Нельзя давать полную аналитику в Free** | Иначе нет драйвера на Starter/Growth; Free остаётся **частью картины**, не клоном Growth. |
| **Нельзя блокировать пользователя до получения ценности** | Жёсткий paywall / полное отключение чтения данных **до** first value moment (при готовых данных) запрещён по продуктовой логике плана. |
