# BoardIQ — инварианты модели доступа (обязательные)

Эти правила **обязательны** для текущей модели доступа. Любые изменения в `billingShellResolver`, `billingExperienceTier`, `billingCurrentPlan`, `requireBillingAccess` и связанных route handlers должны **сохранять** эти инварианты.

Контекст и таблицы состояний: [BILLING_ACCESS_MODEL.md](./BILLING_ACCESS_MODEL.md).

---

### 1. Free как дефолтный вход в продукт

- `access_state === "no_subscription"` **не** означает hard PAYWALL по умолчанию.
- Пользователь без подписки, который находится в продуктовом флоу, должен трактоваться как **Free**.
- `/app/projects` является допустимой точкой входа для Free-пользователя.
- Новый пользователь не должен попадать в `PAYWALL` только из-за отсутствия подписки.

### 2. PAYWALL не является дефолтным сценарием для no_subscription

- `PAYWALL` не должен возвращаться как типичный shell для `no_subscription`.
- `PAYWALL` допустим только как legacy/fallback/специальный сценарий, но **не** как основной путь нового Free-пользователя.
- Для типичного нового пользователя `no_subscription` ожидаемое состояние — **`DASHBOARD` + `OK`**.

### 3. UI не может обещать больше, чем разрешает API

- `allowed_actions` и кнопки в UI должны быть подмножеством того, что разрешают `canReadAnalytics(...)` и `canRunSync(...)`.
- Если API запрещает sync, UI не должен показывать `sync_refresh`.
- Если API запрещает read, UI не должен создавать впечатление, что аналитика доступна.

### 4. API — источник истины для read/sync

- Истина по доступу к данным определяется функциями:
  - `canReadAnalytics(...)`
  - `canRunSync(...)`
- Shell и клиентский UI обязаны быть синхронизированы с этими функциями.
- При конфликте между shell/UI и API корректируется **shell/UI**, а не наоборот, если отдельно не принято продуктовое решение.

### 5. Free участвует в лимитах так же, как paid

- Если для Free задана матрица с конечными `max_*`, то эти лимиты должны **реально** применяться.
- Free должен участвовать в over-limit расчёте наравне с paid, если состояние **не** относится к read-only/blocked классам.
- Первый проект для Free разрешён; превышение начинается только после достижения лимита.

### 6. Over-limit и READ_ONLY не должны конфликтовать

- Состояния `paused`, `unpaid`, `expired`, `refunded` не должны одновременно давать основной UX через `OVER_LIMIT`.
- Для этих состояний приоритет имеет billing shell (`READ_ONLY` / `REFUNDED` и т.д.).
- Over-limit не должен подменять read-only сценарий.

### 7. Ошибка bootstrap ≠ отсутствие подписки

- Ошибка загрузки billing/bootstrap не должна интерпретироваться как `no_subscription`.
- Ошибка gate/bootstrap должна иметь отдельный технический сценарий (`BILLING_GATE_UNAVAILABLE` / **503**), а не ложный billing block.
- Пользователь не должен видеть сообщение «нужна подписка», если реальная причина — ошибка загрузки billing-контекста.

### 8. Free ≠ unpaid / expired / paused

- **Free** — это продуктовый доступ без подписки (`no_subscription` + политика tier).
- `unpaid`, `expired`, `paused`, `refunded` не должны автоматически трактоваться как Free.
- Для этих состояний действуют отдельные правила shell/read/sync.

### 9. Матрица плана не должна расходиться с enforcement

- `plan_feature_matrix` должна быть единым источником ограничений по ресурсам и фичам.
- Если фича ограничена в UI, сервер не должен отдавать полный payload в обход этого ограничения.
- Если сервер ограничивает фичу, UI не должен показывать её как полностью доступную.

### 10. /app/projects должен оставаться рабочей точкой входа

- Пользователь Free должен иметь возможность дойти до `/app/projects` и создать первый проект.
- Кнопка создания первого проекта не должна блокироваться преждевременно.
- Лимит проекта для Free применяется **после** достижения лимита, а не до первого создания.

### 11. Sync-политика должна быть единообразной

- Для `past_due` / `grace_past_due` UI не должен показывать sync, если `canRunSync(...) === false`.
- Нельзя допускать сценарий, где пользователь нажимает видимый sync и получает **402** только из-за рассинхрона shell/API.

### 12. Любое изменение billing-логики требует повторной проверки

После любых изменений в:

- `billingShellResolver`
- `billingExperienceTier`
- `billingCurrentPlan`
- `requireBillingAccess`
- `planConfig`
- route handlers с billing-gates

нужно перепроверять минимум:

- Free 0 → 1 проект  
- Free превышение лимита  
- paid normal flow  
- past_due / grace sync visibility  
- paused / unpaid / expired read-only  
- bootstrap failure / 503 path
